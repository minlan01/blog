# 专家团机制实测报告

> 测试场景：Blog P0 基线治理
> 测试时间：2026-07-26
> 被测成员：architecture-governor（构思远）

---

## 一、什么能用

| 能力 | 状态 | 说明 |
|------|------|------|
| Agent 工具调度成员 | ✅ 可用 | `subagent_type: "architecture-governor"` 成功触发 |
| 成员产出专业分析 | ✅ 可用 | 返回 10 条发现 + 8 条风险 + 2 条 ADR，质量高 |
| 主理人中转信息 | ✅ 可用 | 我把 P0 变更清单写进 prompt，成员基于此分析 |
| 成员之间不直连 | ✅ 自然保证 | Agent 工具每次调用是无状态的，成员之间无法通信 |
| Gate 裁决流程 | ✅ 可用 | 成员输出 VERDICT，主理人决定是否推进 |

## 二、什么不能用 / 有缺陷

### 问题 1：成员无法读文件

**现象**：`architecture-governor` 明确说"我无法直接读取本地路径文件"，只能基于 prompt 里的描述做分析。

**后果**：
- 5 条发现是**假阳性**（F-003 单例缓存、F-006 set -e、F-007 diff_schema 维度、F-009 占位命令、F-010 表顺序）--这些在代码里已经正确实现，但成员看不到源码所以提了出来
- 成员无法做真正的"代码级审查"，只能做"架构级分析"

**根因**：Agent 子进程没有文件系统权限，与主理人的工作区隔离。

### 问题 2：TeamCreate 不存在

**现象**：SOP 里写的"TeamCreate 建立团队"没有对应的工具。

**实际替代方案**：Agent 工具本身就是调度机制。主理人按 SOP 阶段传入成员 ID + 任务描述即可。不需要单独的"创建团队"步骤。

**但 SOP 文本仍然要求 TeamCreate**，这会让人困惑。

### 问题 3：每次调用是一次性的

**现象**：Agent 工具是"一问一答"模式，没有持续会话。

**后果**：
- 成员无法追问"你能把那个文件再读一遍吗"
- 成员无法做多轮分析（比如先读文件 -> 发现问题 -> 再深入查）
- 主理人如果想补充信息，需要重新发起一次调用

### 问题 4：上下文完全依赖主理人

**现象**：成员的知识边界 = 主理人传入的 prompt 内容。

**后果**：
- 如果主理人漏传关键信息（比如忘了传某个文件的变更），成员就看不到
- 成员的分析质量上限 = prompt 质量上限
- 主理人变成"信息瓶颈"--所有跨成员的信息流都要经过主理人整理和转交

### 问题 5：并发控制不可编程

**现象**：Agent 工具的并发由系统控制，主理人无法设"最大并发 4"。

**后果**：SOP 里的"维护最大并发 4"是一个指导原则而非可编程约束。

---

## 三、调整建议

### 建议 1：SOP 文本调整

| 原 SOP | 建议改为 |
|--------|---------|
| "TeamCreate 建立团队" | "主理人按阶段直接用 Agent 工具调度成员，不需要单独创建团队" |
| "成员作为独立协作方输出" | "成员是无状态分析器，主理人必须在 prompt 中提供完整上下文" |
| "所有跨成员信息流必须经主理人中转" | 保持不变（Agent 工具天然保证这一点） |

### 建议 2：主理人调度模式调整

**当前 SOP**：主理人下发任务 -> 成员自己读文件分析 -> 回传

**建议模式**：主理人**先读文件** -> 把文件内容 + 变更摘要写进 prompt -> 调度成员分析 -> 成员返回发现 -> 主理人汇总

也就是说：**主理人承担"信息桥梁"角色**，把文件内容提取后喂给成员。成员只做"基于给定信息的分析"。

### 建议 3：成员 Prompt 模板标准化

每次调度成员时，prompt 应包含：

```
## 项目上下文
- 技术栈 / 当前状态 / 本次变更范围

## 变更文件清单
- 文件路径 + 变更摘要

## 关键文件内容（主理人已读取）
[文件1完整内容]
[文件2完整内容]
...

## 复核要求
- 按角色职责聚焦
- 输出 FINDINGS / RISKS / VERDICT
```

### 建议 4：成员角色定义微调

| 成员 | 当前定义的问题 | 建议调整 |
|------|--------------|---------|
| 所有成员 | "实现"类职责无法执行（成员不能写文件） | 区分"分析型成员"和"执行型成员" |
| architecture-governor | 定义含"维护"职责，但实际只能"审查" | 明确为"只读审查 + ADR 建议" |
| backend-engineer / frontend-engineer | 定义含"实现"职责 | 标注"在当前环境下，主理人代为实现，成员做方案设计和代码审查" |
| security-governor | 同上 | 标注为"威胁建模 + 审查" |

### 建议 5：Gate 流程简化

当前 SOP 有 G0-G7 共 8 个 Gate。实际执行中：

- G0（基线确认）：主理人直接做
- G1（问题定义完成）：主理人直接做
- G2（设计闭合）：可以调 architecture-governor 审查
- G3（实现完成）：主理人直接做
- G4（集成验证）：可以调 test-automation-engineer 或 security-validation-engineer
- G5-G7（发布）：主理人 + 用户确认

建议把 8 个 Gate 简化为 **3 个关键 Gate**：
- **Gate A（设计审查）**：架构 + 安全成员审查方案
- **Gate B（实现审查）**：架构 + 安全成员审查代码变更
- **Gate C（发布审批）**：独立审查员 + 用户确认

---

## 四、结论

专家团机制**有价值但需要调整**：

1. **核心价值**：成员的视角和专业分析质量确实高，architecture-governor 发现的 F-001（create_all 双路径）和 F-002（seed 幂等性）是真问题
2. **核心缺陷**：成员无法读文件，导致假阳性多、代码级审查做不到
3. **调整方向**：主理人做"信息桥梁"，成员做"基于给定上下文的专业分析"
4. **SOP 简化**：去掉 TeamCreate 步骤，Gate 从 8 个简化为 3 个
5. **角色澄清**：标注"分析型"vs"执行型"，当前环境下执行全由主理人完成
